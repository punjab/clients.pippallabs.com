02 · Architecture

A deliberately boring modular monolith

Rails owns transactions and presentation; explicit ingestion, workflow, and reporting modules preserve seams for later extraction. PostgreSQL owns durable state, jobs, cache, raw events, and audit records.

Client websites

Cookie-free tracker plus server-side lead and job-application forms. Public tracking keys map to one active website.

→

Rails 8.1 application

Public APIs · sessions and policy scope · sales and hiring workflows · metric queries · Hotwire UI · Active Job

→

PostgreSQL 18

Tenant records · immutable events · append-only history · notifications · reports · Solid Queue/cache

Public boundary

64 KB limits, IP rate limits, key digest lookup, field allowlists, plausible timestamps, configured-domain checks, URL validation, tenant-scoped idempotency, and no arbitrary event PII.

Private boundary

Signed HTTP-only sessions derive the current membership. Queries begin from that tenant and add the assigned-location constraint for location managers.

05 · Decisions

Why this stack and shape

01

Rails + Hotwire

One security and transaction boundary, minimal client state, accessible server HTML, and fast pilot iteration without a separate API/SPA release train.

02

PostgreSQL everywhere

Application state, source events, audit, queue, and cache use one operational datastore until measured scale justifies extraction.

03

Application-scoped tenancy

Membership-derived queries plus constraints and request tests are explicit today; row-level security remains a documented later hardening option.

04

Raw facts, derived proof

Reports snapshot the same metric engine as the dashboard. Clicks remain intent; only won actual values count as attributed revenue.

Durable records: ADR-0001 through ADR-0006. Chronology: decision log.

07 · Recommended deployment

Managed pilot first; portable container always

The initial recommendation is Render: one Docker web service, one worker, and one managed PostgreSQL database in the same region. This minimizes pilot operations while retaining a normal Docker image that can later move to Kamal or another provider.

Render web

TLS proxy, health check at /up, zero-downtime deploys, Rails/Puma/Thruster container.

+

Render worker

Solid Queue supervisor, lead alerts, scheduled monthly summaries, visible failed jobs.

+

Managed Postgres

Backups, one connection URL, source records, app data, queue, and cache tables.

render.yaml expresses this topology but nothing has been deployed. See the official Rails 8 deployment guide and managed PostgreSQL documentation.
